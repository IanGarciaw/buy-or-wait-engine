## The problem

Given a person's financial history — salary, recurring debits, pending charges, credit lines, plus
free-text messages and photographed receipts — decide whether they can pay for a purchase **now**,
**in installments**, **later**, or **not at all**, and forecast their cash position over the next
90 days.

Getting the answer *approximately* right is worthless. A wrong "yes" pushes someone into an
overdraft. A wrong "no" denies capacity they actually have. Both failures are silent.

## The architecture

> **The model is not the calculator.**

```
   messages, receipts, photos                    structured financial records
              │                                              │
              ▼                                              │
   ┌──────────────────────┐                                  │
   │  extraction          │  ← the only probabilistic step   │
   │  closed schema only  │    37 model calls / 250 requests │
   └──────────┬───────────┘                                  │
              │        facts with a declared, closed shape   │
              └──────────────────┬───────────────────────────┘
                                 ▼
                   ┌─────────────────────────────┐
                   │  finance — 90-day forecast  │   deterministic
                   ├─────────────────────────────┤   Python.
                   │  decision — eligibility,    │   every amount,
                   │  plans, ranking, safety veto│   date and rule
                   └──────────────┬──────────────┘   is steppable
                                  ▼                  in a debugger
                     status · amount · method · plan
                     earliest date · reasoning
                                  │
                   ┌──────────────┴──────────────┐
                   │  independent verifier       │  re-derives the forecast
                   │  cannot read text or images │  through a separate path
                   └─────────────────────────────┘
```

A language model is excellent at reading a blurry receipt and terrible at being accountable for a
number that decides whether someone makes rent. So it never touches the arithmetic. It converts
unstructured input into facts with a **closed schema declared in code** — and everything downstream
is ordinary, inspectable Python.

The verifier is the structural defense: it re-implements the 90-day forecast through a different
code path and is *deliberately denied* access to the messages and images. When the two agree, that
agreement means something. Two components sharing one wrong assumption cannot produce it.

## The rule that governed the design

> **The scope of a message's effect may not exceed the scope of its evidence.**

This single sentence resolved four independent defects in the final hours:

| Message | What the engine did | What the evidence supported |
|---|---|---|
| *"my income ended"* | switched off **every** income stream | only the stream it named |
| *income date change* | kept the new date, **discarded the amount** | the message declared both |
| *one late payment* | installed a **permanent** salary cut | a single delayed deposit |
| *"not yet in cash"* | erased a payroll line for varying | a variance, not a disappearance |

Every one produced the same artifact: a **false zero** — real capacity the engine deleted. Twelve
rows, one root cause. Finding the sentence was worth more than finding the four bugs.

## How it is verified

Verification is not a phase at the end here. It is most of this repository.

| Mechanism | What it establishes |
|---|---|
| **Specification oracle** | 8 invariants (S1–S8) evaluated against all 250 real rows. The falsifier is the production corpus, never a fixture written to agree with me |
| **Mutation suite** | 32 deliberate defects injected into the engine; **32 caught**. Every guarantee ships alongside the mutation that turns its own test red |
| **Independent verifier** | Second implementation of the forecast on a separate code path, blind to free text and images |
| **Clean-room reproduction** | Output regenerated byte-for-byte (SHA-256 match) in an isolated environment, twice |
| **Tagged benchmark** | Scored per release tag against a labelled sample held disjoint from the production set, so a gain can never come from fitting the test |
| **Line-by-line compliance audit** | Each clause of the written specification mapped to the code that satisfies it, and to the test that would fail without it |

### Why the mutation suite exists

**A check that has only ever been seen green has not proven it can go red.** A passing test suite is
consistent with a suite that tests nothing. The only way to know an instrument works is to break the
thing it watches and confirm it screams. So every invariant has a matching sabotage, kept in the
repository, and the suite is judged by how many of its own sabotages it catches — not by how green
it looks on a good day.

## What was measured and rejected

Turning down a change on evidence is worth as much as shipping one. Each of these was implemented,
measured against the real corpus, and dropped:

- **Removing the 90-day floor veto** produced the best score of any variant — and violated an
  explicit line of the specification. The contract won over the scoreboard.
- **Not reserving pending debits** gained points across three metrics and contradicted a literal
  instruction.
- **Moving the staleness threshold** changed **0 of 250** rows. Closed, with the measurement
  recorded so nobody reopens it.
- **A semantic-scope rule for one message class** moved 13 rows, but its value depended on an
  approved invoice payment that appears in no source. Asymmetric risk, no falsifier, out.

The three points lost between two release tags were spent deliberately: an explicit clause of the
specification required a hard veto that the higher-scoring variant ignored.

## Layout

```
code/
  extraction/    closed-schema extraction from text and images
  finance/       the deterministic 90-day cash-position model
  decision/      eligibility, payment plans, ranking, safety veto
  evaluation/    specification oracle, labelled samples, fixtures
  audit/         invariant checks over the full output
  forensics/     per-case traces for disputed decisions
  riesgo/        recorded incidents and their root causes
  compliance/    clause-by-clause audit against the specification
  release/       packaging, hashing, clean-room reproduction
```
